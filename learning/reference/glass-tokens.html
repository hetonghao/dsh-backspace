玻璃 token 清单

配套课程：第 6 课。 本页回答两个问题：每个 token 该多透明，以及 Harness 升级后怎么重新确认。

本页数字会过期 下表基于本机安装的 Harness 0.2.1。 消费方统计随版本变化，页尾的重新生成方法才是长期有效的部分。

结论：按语义分层

token语义透明度原因
--dsw-alias-bg-base 工作区表面 跟随玻璃设置 这就是"让海面透出来"的那一层
--dsw-alias-bg-layer-1 浮在工作区上的 UI 0.97 固定 悬停预览卡、输入框外壳、选中指示器
--dsw-alias-bg-layer-2 更上层浮层 0.97 固定 弹窗、浮动窗、胶囊按钮
--dsw-alias-bg-layer-3 小控件 跟随玻璃 标签、按钮、输入框，面积小、影响可接受
--dsw-alias-bg-module-platform 模块容器 跟随玻璃 + 0.02 标签页、中性标签
--dsw-alias-bg-multi-select 多选态 跟随玻璃 + 0.02 面积小
--dsw-alias-bg-overlay （当前零消费） 跟随玻璃 + 0.10 覆盖无害；但当前版本无元素使用
--dsw-specific-sidebar-fill 侧栏填充 玻璃 − 0.04 侧栏比对话区略深一点
--dsw-specific-selector 选择器 跟随玻璃 + 0.02 小控件
0.97 这个数从哪来 不是拍脑袋：它是设置弹窗早在 1.2.5 就在用的值。 统一到同一个数字，才能让"什么算浮层"只有一个答案。 低于 0.96 时，弹窗里的长文本叠在海面上会明显发花。

历史：四次同类事故

版本症状真实原因
1.2.1设置弹窗被对话输入框盖住，点不到 给列加 z-index 造出了层叠上下文，把弹窗困在里面
1.2.3侧栏比对话区浅，三栏深浅不一 侧栏叠了半透明填充 + 透明覆盖规则互相打架
1.2.5对话区比两侧暗，中间发黑 嵌套表面各自半透明，alpha 复合了两次
本次悬停预览卡（diff 弹层）文字透出背景 把浮层 token 也和玻璃一起稀释了
共同机制 插件假设了某个 token / 元素的用途，Harness 拿它去画了别的东西。 四次症状不同，机制相同。修法必须从"补元素"升级为"按 token 语义分层"。

alpha 会复合：唯一必须记住的硬约束

两层半透明叠在一起，最终不透明度是 1 − (1−a)(1−b)，不是相加。 

0.6 上再叠 0.6 → 1 − 0.4×0.4 = 0.84    （比任何单层都深）
0.4 上再叠 0.4 → 1 − 0.6×0.6 = 0.64

所以：想得到某个最终透明度，就必须控制"有几层在叠"。 1.2.5 的"对话区偏暗"、独立对话背景不得不把框架填充交还各列，都是这条约束的产物。

怎么重新生成这份统计

Harness 升级后，按这个流程重新确认（macOS 官方客户端）：

# 1. 解包前端（一次性）
npx --yes @electron/asar extract \
  "/Applications/DeepSeek Harness.app/Contents/Resources/app.asar" \
  /tmp/asarprobe

CSS=/tmp/asarprobe/dsh/node_modules/@deepseek-ai/dsh-web-frontend/dist/assets

# 2. 统计每个 token 被哪些选择器消费
cd "$CSS" && node -e '
const fs = require("fs");
const css = fs.readdirSync(".").filter(f => f.endsWith(".css"))
  .map(f => fs.readFileSync(f, "utf8")).join("");
const toks = ["bg-base","bg-layer-1","bg-layer-2","bg-layer-3","bg-overlay"];
for (const t of toks) {
  const hits = [];
  for (const r of css.split("}")) {
    if (r.includes("var(--dsw-alias-" + t + ")")) {
      hits.push(r.slice(r.lastIndexOf("}") + 1).split("{")[0].trim());
    }
  }
  console.log(t, hits.length, hits.slice(0, 4).join(" | "));
}'
判定原则 消费方里有"浮在工作区之上"的元素（弹窗、预览卡、浮动窗）→ 必须不透明。
只有"工作区本身" → 跟随玻璃。
拿不准时，选不透明：读不清文字比不够通透严重得多。

改动这一层时的检查清单

  • 改的是 token 还是具体元素？优先改 token。
  • 新规则会不会导致多层叠加？数一下从根到目标的半透明层数。
  • 新的 !important 会不会盖掉设置弹窗的独立规则？
  • 深色模式有没有对应的值？（两套都要改，别只改浅色）
  • 改完跑 npm run test:desktop，它会断言各列最终透明度和浮层 token。
