脱离上游：哪些能去，哪些不能

"不署名、独立发展"这个目标里藏着三件性质完全不同的事： 法律义务（不能改）、品牌整理（该改）、工程解耦（要改）。 把它们混在一起谈，很容易为了"看起来干净"而违反许可协议。

1先分清三件事

2一个必须正视的事实：你的代码占比

我用 git blame 逐行统计了当前 HEAD 的归属。这不是道德评判， 只是让你知道"独立发展"现在站在什么地基上：

文件行数你（HTH）上游作者说明
shared/skin-core.js749 263386 唯一你大量参与的文件
shared/ocean.js637 6631 渲染器几乎完全上游
shared/styles.css367 1366 样式表原封未动
plugin/index.js79 574 Host 路由上游写的
全仓库（含文档/vendor）18759 1928— 约 10%
这意味着什么 现在删掉上游署名，技术上能做，但作品实质仍是上游代码—— 这既不符合开源社区的惯例，也不利于你长期维护（因为你不熟悉那 90%）。 更务实的目标不是"删署名"，而是"把署名保持在正确的位置，同时让自己的代码变成主体"。

3第一步：先搞清楚"上游"现在是什么状态

很多人以为 fork 之后就"停在当时那版"了。实际不是。我查了真实状态：

当前同步状态（2026-10-19 实测）

  • 上游 d-dev0101/open-sea-skin 的 main 停在 634583f。
  • 本仓库已包含上游全部提交（upstream ahead = 0），本地领先 4 个提交。
  • 也就是说：现在没有落后的上游修复，历史是干净的。

这是个好消息——意味着"脱离上游"不会让你丢失任何当前已知的修复。 这个结论现在成立，但不会永远成立：上游随时可能提交新东西。

GitHub 上本仓库仍是 fork: true，属于 d-dev0101/open-sea-skin 的 fork 网络。 这不是 git remote，删掉 upstream 远程不会消除它。 要脱离 fork 网络，必须在 GitHub 侧操作（Settings 里没有直接的"脱离 fork"按钮， 常见做法是让 GitHub Support 解除，或新建一个非 fork 的仓库迁移过去）。

一个我自己做不了的操作 解除 GitHub fork 关系需要你在 GitHub 后台或联系 GitHub Support， agent 无法代劳。如果你决定这么做，我可以帮你把迁移步骤和影响面列清楚。

4可执行的脱钩清单

按"风险从低到高、可逆性从高到低"排序。每一项都标了可逆性。

步骤操作可逆影响
1 删 upstream remote
git remote remove upstream		 是（随时可加回） 不再能 git fetch upstream；fork 网络标记仍在
2 打通 npm 发布
npm login → npm publish		 否（版本号一旦发布不可删） 修掉当前文档缺陷：文档让用户装的 dsh-backspace@1.2.5 现在根本不存在
3 清理 site/ 的「OPEN SEA」字样 否（测试锁 SHA-256，需同步改） 该目录不在发布包内；改它收益小、成本中
4 统一两套配置来源 是 消除字段漂移（第 2 课那个缺陷）
5 给现有 slot 写正规设置面板
（settings.section）		 是 摆脱 DOM 自绘，改善可维护性
6 逐步弃用 harness-plugin/
（源码注入路径）		 是（保留目录即可回退） 减少一个维护面；但它目前提供唯一的背景层
7 解除 GitHub fork 关系 否 需 GitHub 侧操作；会让 PR/issue 关联断裂
8 重写渲染器以降低上游代码占比 否 工作量最大，但这是"作品真是你的"唯一实质路径
我的建议顺序 2 → 4 → 5 → 1 → 6。 理由：第 2 步是当前唯一的功能性缺陷（用户按文档装不上），优先级最高； 4 和 5 是真正的技术债，直接决定你后面的扩展效率； 1 和 6 是"心理上的干净"，可以晚点做； 7 和 8 别急——在你自有代码占比上来之前做 8 意义不大。

5关于 MIT 署名，把话说明白

MIT 协议只有一条硬性要求（原文用 Permission is hereby granted … subject to the following conditions 引入）：

The above copyright notice and this permission notice shall be included in all copies or substantial portions of the Software.

翻译成可执行的话：

  • 可以：改名、换标识、闭源分发你的新增部分、商业化、不再提"我们是 fork"。
  • 必须：随软件附带那份包含原始版权行和许可全文的文本。
  • 不存在：MIT 里没有任何"必须写致谢""必须链接上游仓库"的要求。

所以 THIRD_PARTY_NOTICES.md 里那段"Backspace is a fork of open-sea-skin" 严格说是超额履行——是礼貌，不是义务。你可以把它改写成更中性的 "基于 MIT 许可的第三方代码"，但那份包含版权行的 LICENSE 文本本身不能少。

当前 LICENSE 的写法其实是对的

Copyright (c) 2026 Open Sea Skin contributors (upstream: d-dev0101/open-sea-skin)
Copyright (c) 2026 Backspace contributors

两行并列，各归各。这既满足了 MIT，也清楚地表明了你的著作权。 如果哪天你想让"Backspace"更突出，可以调整行序或措辞， 但不要删掉第一行。

7延伸阅读

  1. MIT 许可证原文（OSI） ——只有三段，两分钟读完。重点就是那句 shall be included in all copies or substantial portions of the Software。
  2. LICENSE 和 THIRD_PARTY_NOTICES.md ——对照上面原文，看当前写法哪些是义务、哪些是超额礼貌。
  3. docs/releasing.md ——发布流程已经写好了，包括 npm 那一步。它缺的不是文档，是真的执行过一次。

这一步涉及法律，我的建议只到"怎么做不违约"。具体商业决策（要不要彻底断、 要不要换许可证、要不要说"基于开源项目"）建议你自己拿主意， 有问题可以追问，我也可以帮你把每种选择的后果列清楚。
