Backspace 课程 · 第 1 课

一份源码，三条路径

你要扩展这个插件，第一件必须刻进肌肉记忆的事： 仓库里只有一份真正的代码，其余同名文件都是它生成的副本。 分不清这一点，后面每一个扩展都会改错地方。

1构建期：谁生成了谁

仓库根目录看起来有一堆重复文件——extension/ocean.js、 native-dist/ocean.js、harness-plugin/assets/ocean.js 三份内容一模一样。这不是历史遗留，是刻意的设计：一份源码，三个交付形态。

三个必须记住的细节

  1. plugin/client.js 不是简单复制。 它被包进了 Harness 的模块加载器壳里（window.__ModuleLoader__.load(...)）， 并把存储适配器直接内联进去——因为这个文件要在浏览器里通过 /plugins/dsh-backspace/client.js 被加载，拿不到构建期的相对路径。
  2. plugin/index.js 是手写的，不是生成的。 它是 Host 侧插件（注册 /dsh-backspace 静态路由），和 client.js 放在同一个目录但来源完全不同。改路由逻辑要改它，改渲染逻辑不要碰它。
  3. 两个适配器是同一份控制器的两种存储后端。 skin-core.js 刻意不含 import/export，靠字符串拼接接到适配器后面。 这就是为什么它长得像 IIFE——那是拼接的前提条件。

2为什么手改生成物一定会炸

npm run check 会跑 build-runtime.mjs --check 和 build-dsh-bundle.mjs --check。这两个脚本不做"重新生成"， 而是重新算一遍期望内容，逐字节比对现有文件，不一致就抛错： 

// scripts/build-runtime.mjs
if (check) assertSame(body, target)
else {
  mkdirSync(dirname(join(root, target)), { recursive: true })
  writeFileSync(join(root, target), body)
}

所以手改 native-dist/loader.js 的后果不是"下次构建被覆盖"， 而是下一次 CI 直接红。这是好事：它把"改错地方"从 运行时怪 bug 变成了构建期硬失败。

常见踩坑 改完 shared/skin-core.js 后忘记跑 npm run build， 就去 `npm run test:desktop` 验证——测试跑的是生成物， 你会看到"改了没生效"，然后开始怀疑人生。构建和验证的顺序是固定的。

3运行期：控制器和渲染器怎么通信

渲染器跑在一个同源 iframe 里，控制器跑在宿主页。两者不是共享内存， 而是靠 URL 参数（初始）和 postMessage（后续更新）。 理解这条边界，是后面加新背景的关键——你的新背景极可能也要走同样的结构。

为什么这对扩展很重要 skin-core.js 只依赖两个注入进来的能力：assetUrl(path) 和 storage（get/set/可选 listen）。 只要你不打破这两个接口，新增任何背景类型都能自动跑在三条路径上。 反过来，一旦你的新功能需要额外的宿主能力，就得三处都改——这是第 2 课的核心。

5延伸阅读

本课的主要依据是代码本身，不是文档。优先级排列：

  1. scripts/build-runtime.mjs ——全仓库对"谁生成了谁"最权威的描述，不到 90 行，建议完整读一遍。
  2. scripts/build-dsh-bundle.mjs ——同样不到 80 行，重点看 adapter 常量。
  3. docs/architecture.md ——文档版总结，适合复习；但注意它描述的是设计意图， 个别地方已经落后于代码（第 3 课会指出一处）。

有不清楚的地方直接问我。比如"为什么适配器要拼接而不是 import"、 "能不能把 skin-core.js 改成 ESM 再打包"——这类问题往往牵出整套设计的取舍， 值得展开讲。
