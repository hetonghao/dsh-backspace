扩展接缝地图

你最关心的问题：想加新背景、加配置项，是只能写代码，还是可以做成壁纸/视频？ 答案取决于你扩展的是哪一层——这个仓库其实有四层接缝，难度和成本差一个数量级。

1四层接缝，按成本从低到高

"能不能不写代码"这个问法太粗。真正有用的问题是： 这个需求能不能被现有接口表达成一个"数据"。 四个层次分别对应四种答案。

2接缝 ②：新背景到底能不能"不写代码"

直接回答：不能完全不写代码，但可以把代码量压到很小，并且让用户零代码换素材。 区别在于"写代码"是一次性的还是每次换素材都要写。

方案要写什么用户可换素材存储可行性
静态图片壁纸 一个 <img> 页面 是（选本地图） IndexedDB Blob 已验证可行
视频背景 一个 <video loop muted> 页面 是（选本地视频） IndexedDB Blob 已验证可行
渐变 / 纯色 几行 CSS 是（调色） localStorage 就够 最简单
程序化（粒子/噪声） 新的 TSL 节点图 否（参数可调） localStorage 需要着色器功底
远程视频 / 直播流 一个 <video src> 是（贴 URL） 一个字符串 可行，但破坏"零网络请求"承诺

为什么"壁纸/视频"这次真的可以，而以前的架构挡住它

现有适配器把设置存在 localStorage 里，而 localStorage 只能放字符串。 我实测过：塞 6MB 进去会直接抛 QuotaExceededError。 一个视频动辄几十 MB，走老路必然失败。

但另外两条实测结果给出了出路：

① 同源 iframe 能读到父页面的 blob: URL。

在父页面 URL.createObjectURL(blob)，把得到的 blob:http://… 字符串作为查询参数传给 iframe（或 postMessage 过去）， iframe 里 fetch() 它会返回 200 且内容一致，可以直接喂给 <video src>。

这意味着：素材不必编码进代码，也不必塞进 localStorage——它可以是用户运行时选的文件。

② IndexedDB 能存 Blob，并能还原。

实测写入 3MB 的 Blob（video/mp4）后读回：仍是 Blob、 size 与 type 都正确、createObjectURL 可用。 这是壁纸/视频该用的持久化层。

别忘了降级 localStorage 在隐私模式或受限环境会直接抛异常（现有代码已经用 try/catch 兜住）。IndexedDB 同理需要兜底：读失败就退回程序化海洋， 绝不能让整个皮肤因为素材读不出而白屏。

最小可行改造：加一个背景类型开关

不需要推翻现有结构。最小改动是让 skin.html 支持按查询参数选背景类型， 控制器只多传一个字段。伪代码： 

// skin.html 仍是唯一入口，只是按 type 分派
const type = new URLSearchParams(location.search).get('type') ?? 'ocean'
if (type === 'ocean') import('./ocean.js?skin=1')
if (type === 'image') import('./background-image.js')
if (type === 'video') import('./background-video.js')

// background-video.js —— 全部内容大约就这么点
const src = new URLSearchParams(location.search).get('src')  // blob: 或 https:
const video = document.createElement('video')
video.src = src; video.muted = true; video.loop = true
video.playsInline = true; video.autoplay = true
video.style.cssText = 'position:fixed;inset:0;width:100%;height:100%;object-fit:cover'
document.body.append(video)
await video.play().catch(() => { /* 自动播放被拦：保持首帧或退回海洋 */ })
document.body.classList.add('ready')   // 复用现有的淡入契约

注意最后一行：document.body.classList.add('ready') 是现有页面淡入的契约 （styles.css 里 body.ready > canvas 靠它触发）。 新背景必须遵守这条约定，否则要么不显示，要么闪一下。

这才是"可以通过壁纸、视频生成"的真实含义 不是"用户完全不用碰代码"，而是：你写一次背景类型，用户之后换任何素材都不用再改代码。 而且这些素材可以是本地的、可以是 AI 生成的、可以是下载的——对代码完全透明。

3接缝 ③：配置管理的真实成本

你现在可能觉得"加个配置项"很简单。看看加 chatOpacity 这一个数字， 上一次提交动了哪些文件：

一个已经存在的技术债，值得你现在就知道

仓库里有两套配置机制并存，字段已经不一致了：

路径声明位置字段持久化
DSH bundle
（plugin/client.js）		 shared/skin-core.js
的 DEFAULTS		 enabled, sea, time, glass,
autoCycle, chatCustom, chatOpacity		 宿主页 localStorage
源码注入
（harness-plugin/）		 settings-contract.ts
＋ settings.ts（zod 校验）		 enabled, sea, time, glass,
autoCycle, quality		 Harness 设置服务
这是一个真实缺陷，不是理论问题 chatCustom / chatOpacity 在源码注入路径里根本不存在； 反过来 quality 在 bundle 路径里也不存在。 也就是说：走 harness-plugin/ 装的人，看不到这次的对话面板独立背景。 两条路径各有一份字段清单，靠人工保持一致——这必然会漂移。

这个缺陷本身就是"配置管理该怎么做"的最好教材：只要你让同一份配置有两个真相来源，它们就会分叉。 第 5 课讲怎么收敛到一个来源。

4接缝 ④：什么时候必须动 Harness

原则上：越少越好，因为改动会在 Harness 升级时失效。 但有些事绕不开。判断标准只有一条——你想注册的那个 slot，宿主是否已经声明了。

我扒了本机安装的 Harness 0.2.1 里 dsh-client-ui-layout 的实际声明， 根节点只有这 6 个： 

"sidebar":       { kind: "single", scope: "root" }
"main":          { kind: "keyed",  scope: "root" }
"rightbar":      { kind: "single", scope: "root" }
"shell.bottom":  { kind: "single", scope: "root" }
"shell.overlay": { kind: "list",   scope: "root" }
"shell.leading": { kind: "single", scope: "root" }
这里没有任何 background slot 所以你不能通过正常插件注册一个"铺在最底层的背景层"。 这正是 harness-plugin/install-into-harness.sh 必须去改 Harness 源码 ui-layout 的原因——它硬插了 'shell.background' 这个声明。

但反过来，已经存在的 slot 是可以被第三方 npm 插件注册的。 这不是推测——我查了本机装的其他插件，它们正在这么做：

已安装插件注册的 slot用途
dsh-model-visibilitysettings.section在设置里加自己的页面
dsh-rewind-pluginplugins.bundle.config插件配置面板
dsh-browser-usesettings.section设置页
对你最重要的一条结论 「配置管理」不需要动 Harness。 settings.section（整页设置）和 settings.general.item（设置里的一个条目）都是现成的 slot， 第三方插件能注册。你现在用 DOM 自绘面板，是因为 bundle 路径最早只需要这样； 要做"正经的配置管理"，正路是注册 settings.section。

5检验一下

1加一个视频背景，主要触及哪一层接缝？

2视频素材为什么不能沿用现有 localStorage 存储？

3做「正经配置管理」需要修改 Harness 源码吗？

4两套配置机制目前是否已经不一致？

6延伸阅读

  1. shared/skin-core.js ——重点读 createController(options)：注意它只要求 assetUrl 和 storage 两个能力，这就是全部的接缝契约。
  2. harness-plugin/src/settings-contract.ts ——只有 30 行，是"配置该长什么样"的好范例（带 zod 校验、带类型）。 对比它在 bundle 路径里的缺失，就能看出重构方向。
  3. deepseek-harness 仓库 ——查 packages/client/ui-* 里各包的 children 声明， 这是目前唯一能确定"哪些 slot 存在"的方法。

想深入哪个方向都可以问我。比如："能不能让视频背景和海洋做成可叠加的图层"、 "IndexedDB 存视频的容量上限怎么定"、"settings.section 注册具体怎么写"。
