玻璃层：为什么它反复出问题

这是全仓库唯一一个修了四次还在修的模块，而你的扩展计划正好要经过它。 本课不讲"玻璃怎么写"，而是讲为什么它必然会坏、以及怎么让它坏得可预测—— 这决定了你之后每加一个背景要付多少维护成本。

1先看证据：同一个根因，四次事故

我把 CHANGELOG.md 和提交历史里所有和玻璃相关的修复排在一起。 注意它们看起来是完全不同的 bug：

2机制：为什么覆盖 token 特别危险

Harness 的配色不是"给每个元素写死颜色"，而是语义 token： 先定义静态调色板，再把语义别名映射上去。 

/* 静态调色板：值 */
--dsw-static-neutral-bluish-00: #fff
--dsw-static-neutral-bluish-950: #151517

/* 语义别名：用途。这就是"token" */
--dsw-alias-bg-base: var(--dsw-static-neutral-bluish-00)
--dsw-alias-bg-layer-1: var(--dsw-static-neutral-bluish-00)
--dsw-alias-bg-layer-2: var(--dsw-static-neutral-bluish-00)

这个设计对 Harness 是好事：改一处调色板，全站跟着变。但对你这个插件， 它意味着一次覆盖会命中所有消费方，而你不知道消费方有哪些。

3实测：哪些 token 真的该透明

我把当前 Harness 前端产物解包，统计每个 token 被多少条规则消费、被谁消费。 这是判断"该不该覆盖"的唯一可靠依据。

token消费规则数消费方插件应如何处理
--dsw-alias-bg-base7 工作区表面、编辑器、背板 跟随玻璃
--dsw-alias-bg-layer-14 悬停预览卡、输入框外壳、选中指示器 保持不透明
--dsw-alias-bg-layer-23 弹窗、浮动窗、胶囊按钮 保持不透明
--dsw-alias-bg-layer-34 标签、按钮、输入框（都是小控件） 跟随玻璃（影响小）
--dsw-alias-bg-overlay0 当前版本无人使用 覆盖无害，但也无效
--dsw-alias-bg-module-platform2 标签页、中性标签 跟随玻璃（影响小）
两个反直觉的实测结论

① bg-layer-1 不只是"卡片"。 它同时画悬停预览、输入框外壳和选中指示器。所以不能"整个调暗"，只能按语义保持不透明。

② bg-overlay 在当前前端是零消费的。 插件花力气把它的透明度算得精细（light + 0.10，上限 0.96）， 但当前版本没有任何元素使用它。
——这提醒你：不要假设你覆盖的 token 一定有用。它可能只是历史遗留，也可能是给未来功能的预留。

这组数据会过期 上面的消费方统计来自当前安装的 Harness 版本。 Harness 升级后数字会变——所以正确做法不是记住这张表，而是记住怎么重新生成它。 方法见 速查：玻璃 token 清单。

4现在的修法：按语义分层，而不是逐元素打补丁

前三次修复都是"发现哪个元素坏了，给它加例外"。 第四次换了思路：按 token 的语义决定透明度。 

// 工作区表面：跟随用户的玻璃设置
--dsw-alias-bg-base: rgba(255, 255, 255, ${alpha(light)})

// 浮层：固定近不透明，玻璃设置不影响它
const ELEVATED_ALPHA = 0.97
--dsw-alias-bg-layer-1: rgba(255, 255, 255, ${alpha(ELEVATED_ALPHA)})
--dsw-alias-bg-layer-2: rgba(255, 255, 255, ${alpha(ELEVATED_ALPHA)})

0.97 不是随便取的——它是设置弹窗此前已经在用的值 （因为那个弹窗早就被单独处理过）。统一到同一个数字， 意味着以后"什么算浮层"只有一个答案。

为什么是"分层"而不是"修元素"

修元素的逻辑是：已知 N 个坏元素 → 写 N 条规则。N 会随 Harness 版本增长，规则永远追不上。

分层的逻辑是：token 有 M 种语义 → 写 M 条规则。M 由 Harness 的设计决定，增长慢且有限。 你从"追症状"变成"守契约"。

5这对你的扩展计划意味着什么

这是本课最实用的部分。你接下来要做两件事，它们和玻璃层的关系完全不同：

你的计划和玻璃层的关系维护成本
加视频 / 壁纸背景 背景在最底层（iframe, z-index 0）， 玻璃层在它上面。两者不冲突。 低——背景换了，玻璃逻辑不用动
加配置项 如果新配置影响透明度/颜色，就会进入玻璃层。 每加一个，就要判一次"它该作用在哪个 token 上"。 中——需要遵循分层原则，否则重蹈覆辙
一个提前的提醒 如果哪天你想做「背景也要有独立透明度」（类似对话面板独立背景）， 别直接给背景加 alpha——那会和玻璃层复合，得到无法预测的结果。 现有代码里对"独立对话背景"的处理已经踩过这个坑： 为了让对话区比侧栏更亮，它不得不把共享的框架填充交还给各列。 alpha 会复合，这是这一层唯一的硬约束。

7延伸阅读

  1. shared/skin-core.js 的 glassCss() —— 现在这一版是分层写法的实例。 重点看 ELEVATED_ALPHA 的定义与注释，那是这一课的全部结论。
  2. CHANGELOG.md 的 1.2.1 / 1.2.3 / 1.2.5 三条 —— 读它们的"症状描述"而非"修复方案"， 你会看到同一个机制如何伪装成三个不同的 bug。
  3. MDN: color-mix() —— 现有代码用它把 Harness 原生调色板按比例稀释。 理解它，你才能判断某个透明度是"算出来的"还是"叠出来的"。

这一课是前三课的"负重训练"：它把架构知识用在了真实缺陷上。 如果你准备开始做背景或配置管理，建议先回答一个问题再动手—— 「我这个新功能，会改变哪个 token、而那个 token 又被谁消费？」 答不上来就先别写代码，问我。
