Backspace 课程 · 第 5 课

配置管理：收敛到一个真相来源

前面反复出现同一个症状：两套配置机制各有一份字段清单，已经开始漂移。 根因不是"忘了同步"，而是结构上允许有两个真相。 本课讲怎么在设计上消除这种可能。

1问题不是重复，是"两个真相"

重复本身不致命——生成物本质就是重复。真正的问题是： 两份清单都是手写的，谁也不是从谁派生来的。这时候"保持一致"只能靠纪律，而纪律会失效。

2为什么这值得做（而不是记牢就行）

你可能会想："我知道有两套，以后加字段两处都改不就行了。" 三个理由说明这条路走不通：

① 忘记的成本是不对称的

加字段忘了某一边，不会报错——只是那条路径的用户静默失去功能。 你刚从 chatOpacity 的事里见过这个形态。这类缺陷的发现周期是"用户来抱怨为止"。

② 字段数会持续增长

现在 7 个字段已经漂移了 2 个方向。如果做到 15 个，靠人脑同步基本不可能。 每加一个字段，两个方向的漂移概率就翻倍。

③ 它挡住了你要的扩展

你要加"背景类型"——这本身就是一个新字段（bgType）， 还可能要 bgSource、bgBlur、bgDim。 这套配置会迅速膨胀，不先收敛就往上加，是在放大债务。

奥卡姆剃刀视角 这个重构不是新增抽象，而是删除重复：删掉一份手写清单、删掉一批手写 key 映射、 删掉"记得两处都改"这条隐性纪律。净代码量大概率会下降。

3具体怎么做：schema 优先

核心思路：字段声明一次，其余生成。用一个纯数据文件描述所有配置。 

// shared/settings-schema.js —— 唯一真相，纯数据，无逻辑
export const SETTINGS = [
  { key: 'enabled',  type: 'boolean', default: true,
    copy: 'enable',
    storage: { extension: 'skinEnabled',  native: 'bsEnabled' } },

  { key: 'sea',      type: 'number',  default: 45, min: 0, max: 100, step: 1,
    copy: 'sea', control: 'range',
    storage: { extension: 'skinSea',      native: 'bsSea' } },

  { key: 'glass',    type: 'number',  default: 72, min: 40, max: 90, step: 1,
    copy: 'glass', control: 'range',
    storage: { extension: 'skinGlass',    native: 'bsGlass' } },

  { key: 'chatCustom', type: 'boolean', default: false,
    copy: 'chatCustom', control: 'switch',
    storage: { extension: 'skinChatCustom', native: 'bsChatCustom' } },

  { key: 'chatOpacity', type: 'number', default: 100, min: 40, max: 100, step: 1,
    copy: 'chatOpacity', control: 'range',
    // 从属于 chatCustom：开关关闭时隐藏该行
    dependsOn: 'chatCustom',
    storage: { extension: 'skinChatOpacity', native: 'bsChatOpacity' } },
]

然后让构建脚本从它派生一切。这一步和你熟悉的 build-runtime.mjs 是同一个模式：

// scripts/build-settings.mjs（新增）
import { SETTINGS } from '../shared/settings-schema.js'

const defaults = SETTINGS
  .map(f => `  ${f.key}: ${JSON.stringify(f.default)},`)
  .join('\n')

const keysOf = side => SETTINGS
  .map(f => `    ${f.key}: '${f.storage[side]}',`)
  .join('\n')

// 生成 DEFAULTS 块 → 注入 skin-core.js 的占位标记处
// 生成 native KEYS → 注入 native-entry.js
// 生成 extension KEYS → 注入 extension-entry.js
// 生成 TS interface + zod → 注入 harness-plugin/src/
// 全部支持 --check，和现有两个脚本一致
关键约束：不要破坏"无 import" skin-core.js 现在刻意不含 import/export，靠字符串拼接接到适配器后面。 所以派生结果必须以生成的代码块注入，而不是让 skin-core.js 去 import schema。 否则三条路径的拼接机制就崩了。

面板也可以由 schema 生成

现在面板 HTML 是 mountUi() 里一大段手写模板字符串。 用 schema 循环生成可以同时解决"加字段要改模板"和"加字段要改 syncUi"两个问题： 

// 从 schema 生成面板行，而不是手写模板
const rows = SETTINGS
  .filter(f => f.control === 'range' || f.control === 'switch')
  .map(f => f.control === 'switch'
    ? `<div class="bs-row bs-switch">
         <label for="${IDS.panel}-${f.key}">${copy[f.copy]}</label>
         <input type="checkbox" id="${IDS.panel}-${f.key}" />
       </div>`
    : `<div class="bs-row"${f.dependsOn ? ` hidden data-depends="${f.dependsOn}"` : ''}>
         ... range 控件，min/max 来自 schema ...
       </div>`)
  .join('')
收益 做完之后加一个新滑块 = 在 schema 里加一条。 面板、持久化、key 映射、类型、校验全部自动跟上。npm run check 保证产物没落后。 这才是"配置管理"该有的形态。

4用 settings.section 做正经面板

DOM 自绘面板有个结构性缺陷：它是浮在宿主页上的一块外来 UI， 管不了无障碍、焦点、主题继承、键盘导航这些宿主已经解决的问题。 Harness 提供了正规入口。

第 2 课查到：已安装的 dsh-model-visibility 正在注册 settings.section。 它的做法是： 

// 来自已安装插件 dsh-model-visibility 的真实用法
const inject = [
  '@deepseek-ai/dsh-api-remotes',
  '@deepseek-ai/dsh-client-locale',
  '@deepseek-ai/dsh-client-ui-settings',
]

function apply(ctx) {
  ctx.effect(() => ctx.slots.inject('settings.section', () =>
    ctx.slots.register({
      name: 'settings.section',
      id: 'backspace',
      order: 30,
      // 插槽把 id / order / label 投影到设置导航
      // 面板内容由你自己的组件渲染
    }, BackspaceSettingsPage)
  ))
}
先证实再动手 上面是从已安装插件的产物反推的形态，不是我查到的公开文档。 动手前建议：装一个已知能用 settings.section 的插件，确认真机生效， 再照它的写法接入。我也可以帮你把当前版本的 slot props 完整读出来。

另一条更轻的路：保留 DOM 面板，但只作为"快捷入口"， 同时在 settings.section 提供一个完整版。这样老用户习惯不变， 新用户能用到原生设置页。代价是两套 UI 要维护——所以更推荐只做 原生那套，DOM 面板退化为一个纯按钮。

5迁移顺序（避免中途断裂）

阶段 1 那条测试长什么样

test('both config paths expose the same fields', async () => {
  // 从 bundle 侧读 DEFAULTS 的 key
  const core = await text('shared/skin-core.js')
  const defaults = core.match(/DEFAULTS = Object\.freeze\(\{([^}]*)\}/s)[1]
  const bundleKeys = [...defaults.matchAll(/(\w+):/g)].map(m => m[1]).sort()

  // 从源码注入侧读 interface 的 key
  const contract = await text('harness-plugin/src/settings-contract.ts')
  const nativeKeys = [...contract.matchAll(/^\s{2}(\w+):/gm)].map(m => m[1]).sort()

  assert.deepEqual(bundleKeys, nativeKeys)
})

写出来就会立刻看到 chatCustom/chatOpacity/quality 的不一致。 这条测试本身就是这次重构最重要的产出——它防住的不只是现在这两个字段，而是未来所有的漂移。

7延伸阅读

  1. settings-contract.ts ＋ settings.ts ——加起来不到 60 行，是"配置该长什么样"的现成范例：带类型、带 zod 校验、带默认值。 把它作为 schema 的起点，比自己从零设计强。
  2. build-runtime.mjs ——派生+校验这套模式在这个仓库已经跑通了，照抄它的结构（含 --check）即可。
  3. deepseek-harness ——动手接 settings.section 前，先读 packages/client/ui-settings 和相关 slot 声明，别只看我这个速查页（它会过期）。

这一课是四节里最"工程"的，但收益也最大。如果你决定做，我建议从阶段 1 开始—— 那条一致性测试我可以直接帮你写，它本身就是一份"当前债务清单"。
